# wealth-nav-watch

**中国银行代销理财净值的每日增量数据 + 蓝筹分红日历订阅。**

## 仓库里放两样东西

| | 抓的是什么 | 产物 | 怎么用 |
| --- | --- | --- | --- |
| **中行净值** | 中行代销理财每天新披露的净值 | `data/YYYY-MM-DD.csv` | 直接读 CSV |
| **分红日历** | 蓝筹 / 高股息股票的**分红公告** | `calendar/dividend-calendar.ics` | **订阅**（地址见下） |

### 中行净值

每天自动抓一次中行的净值披露页，只把**新增**的净值存成 CSV 推进仓库：
`data/YYYY-MM-DD.csv`，文件名是**数据日**（北京时间）。

```
data/
  2026-11-10.csv     ← 数据日 11-10 的新增净值
  2026-11-11.csv
  ...
```

没有新增数据的那天**不产生文件**（不会出现只有表头的空 CSV）。

### 分红日历（订阅地址）

```
https://raw.githubusercontent.com/bigegao/wealth-nav-watch/main/calendar/dividend-calendar.ics
```

把这个地址丢进日历 App 的「订阅日历 / 从 URL 添加」就行 ——
不用服务器、不用注册，仓库更新了日历就跟着更新。详见下面的「分红日历订阅」。

### 这个仓库是**唯一的抓取点**

抓取放在这里、不放在 [`lanxyou/stock-tracer`](https://github.com/lanxyou/stock-tracer)，
理由有三个：

1. **要跑得久、要抓得多**。中行三个源合计 516 页，跨境单页 1.6~3 秒 ——
   GitHub Actions 一次跑完没有子请求限制；Workers 免费版每次调用只有 50 次子请求，
   抓全站要 5 次调用。
2. **要留历史**。中行归档站每只产品只留最新一条，历史批次一旦被覆盖就**永久消失** ——
   想攒净值序列**只能每天存一条**。这个历史属于「数据仓」，不属于「应用仓」：
   每天往应用仓提交一次数据提交，会把代码变更历史搞脏。
3. **职责单一好排查**。stock-tracer 那边只做导入，不自己抓 ——
   两个地方都抓，出问题时你分不清数据是哪条路来的。

stock-tracer 那边对应的是「中行净值导入」那条流水线（定时拉本仓库的 CSV）；
它自己那条「中行净值补抓」是**手动**的，只在回补历史或上游漏跑时用。

### 陈旧的产品不抓（一两个月没变化）

中行归档站**每只产品只留最新一条**，所以「净值日期老」=「这只产品没再披露过」。
实测全站最后披露日期从 2019-05 一直到 2026-11，尾部一大批已经一两年没动过了。

日常跑：

- **早停**：分块翻页（8 页一块），某一块里**最新的净值日期**都早于「今天 − 60 天」
  → 后面只会更老，收工。实测三个源合计从 **516 页降到 296 页（-43%）**；
- **不入增量**：净值日期早于截止日的行不写进 CSV（实测全站有 1,713 行是这种）。

早停为什么不会漏数据：页序 = 披露批次（页码越小 = 披露日期越新），
产品**再次披露时会回到前面的页** —— 睡着的产品一醒来必然出现在还在翻的前几页里。
万一页序有例外，**每周二（北京时间）凌晨那次跑全量**兜底
（cron 的 `21:00 UTC` = 北京次日 05:00，所以那一轮对应的是 UTC 周一晚上）。

> ⚠️ 阈值 60 天必须与 stock-tracer 的 `BOC_STALE_DAYS` 一致 ——
> 两个仓库各有一份实现（这里零依赖、不 import 那边），数值漂移就会出现
> 「上游写了、下游早停」这种口径不一致。

### 日期规范：数据日 = 抓取日 - 1

| | |
| --- | --- |
| **抓取日** | 脚本实际跑的那一天（北京时间） |
| **数据日** | **抓取日的前一天** —— 文件名与 `data_date` 列都用它 |

**为什么不用抓取日当文件名**：中行按估值日披露、批次在**白天**才刷新，
所以凌晨抓到的必然是「昨天披露出来的那一批」。
实测（中行代销理财，第 1 页）：

| 抓取时刻 | 页面上最新的批次 |
| --- | --- |
| 11-11 11:55 | 11-09 |
| 11-12 03:43 | 11-10 |
| 11-12 14:05 | 11-11 |

如果文件名用抓取日，「2026-11-12.csv」在不同批次下含义会漂 ——
同一天里早上跑和下午跑指的是完全不同的两批数据。
用数据日就只有一个含义：**这一批是什么时候披露出来的**。

⚠️ **GitHub 的 schedule 会延迟**（实测延迟过 7 小时，20:20 的触发落到了次日 03:43），
所以「文件是哪天生成的」和「数据属于哪天」必须分开记 —— 靠数据日。

## 数据从哪来

中国银行「当日代销理财产品净值」静态页：

```
https://www.boc.cn/sourcedb/<目录>/index_<页码>.html
```

纯静态 HTML，**不用登录、不用签名、不用 JS 渲染**。

| `source_dir` | 是什么 | 页数（实测 2026-11） | 行数 |
| --- | --- | --- | --- |
| `srfd6_2024` | 代销**理财** | 196 | 9,798 |
| `srfd2_2024` | 代销**基金** | 121 | 6,031 |
| `srfd3_2024` | 代销**资管** | 199 | 9,949 |

三个源表头完全一致（8 列），格式统一。

## 为什么必须自己攒

**中行这个归档站每只产品只保留最新的一条记录。**

实测（2026-11-11，全站 196 页）：

- 9,798 行 / 9,363 个产品代码；
- 拥有 **≥2 个不同净值日期**的产品 = **0 只**；
- 最后披露日期跨 2019-05 ~ 2026-11，共 1,183 种。

也就是说：**历史批次一旦被新披露覆盖就永久消失**，页面本身查不到历史。
想攒净值序列，**只能每天存一条**。

这也意味着：**本仓库的数据是从第一次运行那天开始攒的**，之前的历史谁也补不回来。

## 增量是怎么判的

去重键 = `(source_dir, code, nav_date)`，**不含** `data_date`。

- 今天新披露的产品 → 新组合 → 进今天的文件；
- 昨天披露过、今天净值没变的 → 组合没变 → 不重复记；
- 中途停跑几天 → 那几天的批次重新出现时会被自动补上（前提是还没被新披露覆盖）。

因为中行是**按估值日披露**的，同一批数据会在页面上停留好几天 ——
所以「今天抓到的」不等于「今天披露的」。真正的披露批次看 `nav_date`。

## 字段

| 字段 | 含义 | 口径 |
| --- | --- | --- |
| `code` | 产品代码 | 中行的**销售代码**（份额代码），不是登记编码 |
| `product_name` | 产品名称 | 原样保留；上游有少量产品名称是空的 |
| `nav_date` | **净值日期** | 中行页面的「截止日期」= **估值日**（不是发布日） |
| `unit_nav` | 单位净值 | 原始字符串，空 = 这一项没有 |
| `cum_nav` | **累计净值** | 含分红再投，**算收益用这个** |
| `period_change_pct` | 期间涨跌幅（%） | 中行第 7 列。表头写的是「日净值增长率」，**实际是相对上一披露日的涨跌幅**，且是**单位净值口径** |
| `per10k` | 每万份基金单位收益（元） | 货币基金口径 |
| `yield7d_pct` | 七日年收益率（%） | 货币基金口径 |
| `source_dir` | 来源静态页 | `srfd6_2024` / `srfd2_2024` / `srfd3_2024` |
| `data_date` | **数据日** | 北京时间，= 抓取日的前一天，等于文件名 |

数值**保留页面上的原始字符串**，不做浮点转换 ——
一是避免精度损失，二是能区分「空」（这项没有）和 `0`（真的就是 0）。

### 两个容易踩的口径

1. **算收益用 `cum_nav`，不是 `unit_nav`。**
   分红型产品两者能差 0.14 倍，拿单位净值算收益会算错，**甚至方向相反**
   （实测同一条记录：用单位净值算三个月是 -0.42%，用累计净值算是 +0.05%）。

2. **`nav_date` 是估值日，不是发布日。**
   一只周五估值的产品，净值会在下周一才出现在这一页上。
   想知道「今天能拿到的最新净值是哪天的」，看 `nav_date`；
   想知道「这批数据是哪天披露的」，看 `data_date`（两者差一天左右）。

## 怎么用

### 当数据看

直接读 `data/` 下的 CSV。想只要理财：

```bash
awk -F, 'NR==1 || $9=="srfd6_2024"' data/2026-11-11.csv
```

### 本地跑一次抓取

需要 Node 18+（零第三方依赖，只用自带的 `fetch`）：

```bash
node scripts/fetch-boc-nav.mjs                # 抓全部源，算增量，写 data/<数据日>.csv
node scripts/fetch-boc-nav.mjs --dry-run      # 只算不写，看看这次会新增什么
node scripts/fetch-boc-nav.mjs --dir srfd6_2024 --pages 20   # 只抓理财的前 20 页
node scripts/fetch-boc-nav.mjs --full         # 全量：不过滤、不早停（回补历史时用）
node scripts/diagnose-network.mjs             # 网络诊断（抓不动的时候先跑这个）
```

参数：

| 参数 | 说明 |
| --- | --- |
| `--dir a,b` | 只抓指定来源（默认三个全抓） |
| `--pages N` | 每个源最多翻几页（默认 220，实际最后一页之后是空页） |
| `--stale-days N` | 净值日期早于「今天 − N 天」的算**陈旧**，不抓不写（默认 60） |
| `--full` | 等价于 `--stale-days 0`：全量翻页，什么都不过滤（回补历史时用） |
| `--dry-run` | 只算不写 |
| `--date YYYY-MM-DD` | 指定**数据日**（产出 `data/<数据日>.csv`；默认 = 昨天） |

### 手动补跑

Actions → **中行净值每日增量** → Run workflow。

### 排查：抓不动的时候

```bash
node scripts/diagnose-network.mjs
```

它会打印：出口 IP、DNS 解析结果（操作系统 + 多个带 ECS 的区域解析）、
**逐个候选 IP 钉住探测**（SNI 仍用域名）、对照站点（百度 / 中行首页 / 中行 sourcedb），
以及 Node fetch 的完整错误链。

Actions 上对应「网络诊断」工作流（手动触发）。

## 为什么抓取不用 `fetch`

2026-11-11 第一次在 GitHub Actions 上跑就挂了，日志里只有一句
`TypeError: fetch failed`，毫无信息量。查下来的原因是**两件事叠在一起**：

1. **IPv6 在 runner 上是黑洞。**
   中行是 geo-DNS，Azure runner 的 `getaddrinfo(www.boc.cn)` 会同时返回
   IPv4 和 IPv6（如 `2409:8731:21f:30:11e::11e`），而 Azure 托管 runner
   没有可用的 IPv6 出口 → `connect ENETUNREACH`。

2. **undici 的 happy-eyeballs 给每个地址只 250ms。**
   跨境 TLS 握手要 3 个 RTT（约 450~750ms），250ms 根本不够 →
   间歇性 `AggregateError[ETIMEDOUT]`，对外只显示成 `fetch failed`。

同一个 URL 连续两次请求，一次成功一次失败 —— 所以这是**概率性失败**，
不是某个节点永久不可用。实测各节点延迟差异也很大：0.8 秒 ~ 13 秒。

所以脚本改成：

- 用 `node:https` 配 `lookup` 覆盖**钉住 IPv4**，`servername` 仍传域名
  （SNI 与证书校验照常，直接连 IP 会证书不过）；
- `agent: false`，每次新建连接，避开服务端提前关 keep-alive 的竞态；
- 一页失败就把**所有候选 IP 轮一遍**，每轮之间重新解析 DNS
  （中行 DNS TTL 只有 300 秒且会轮换节点）；
- 错误链（`err.cause`）完整打印，不再只给一句 `fetch failed`。

改完在 Azure runner 上实测：30 页 16.8 秒，零失败零重试。

## 分红日历订阅

抓**蓝筹 / 高股息**股票的**分红公告**，生成**日历订阅（ICS）**推进仓库，
订阅方用 GitHub raw 直接读。

### 订阅地址

```
https://raw.githubusercontent.com/bigegao/wealth-nav-watch/main/calendar/dividend-calendar.ics
```

日历 App → 「订阅日历 / 从 URL 添加」→ 贴上去。
iOS/macOS 的「日历」App、Apple 日历、Google 日历、Outlook 都能读 ICS。

> 分支还没合进 `main` 之前，用分支地址订阅：
> `https://raw.githubusercontent.com/bigegao/wealth-nav-watch/feat/dividend-calendar-feed/calendar/dividend-calendar.ics`

### 日历里是哪两类事件

| 分类 | 落点日期 | 是什么 |
| --- | --- | --- |
| `分红` | **除权除息日**（没有就退到股权登记日） | 这一天除权除息 —— 真正影响股价的那天 |
| `公告` | **公告披露日** | 某笔分红的预案 / 实施公告出来了 |

两条都必要：**分红**是提醒（哪天该落袋），**公告**是凭据
（这条安排是哪份公告说的，点事件能直接打开公告原文）。

点开一个 `分红` 事件，说明里有报告期、股权登记日、除权除息日、每 10 股派息、
方案进度，以及对应的公告标题与原文链接。

### 抓的是什么

| 数据 | 来源 | 接口 |
| --- | --- | --- |
| **分红方案**（报告期 / 登记日 / 除权日 / 派息 / 进度） | 东方财富数据中心 `RPT_SHAREBONUS_DET` | 由上市公司《利润分配方案公告》整理 |
| **分红公告**（标题 / 披露日 / 原文链接） | 东方财富公告库 `np-anotice-stock` | 公告原文 |

两者按**公告日**对上号：方案的「实施公告日」↔ 公告的「披露日」，
方案的「预案公告日」也留作兜底。

清单在 `config/dividend-watchlist.json`（50 只，口径：沪深主板为主的高股息 /
现金流稳定的蓝筹，兼顾银行、能源、交通、消费、医药）。
清单本身来自 [`lanxyou/stock-tracer`](https://github.com/lanxyou/stock-tracer)
的 `shared/data/default-watchlist.ts` —— 搬过来是因为**抓取放数据仓**，
改口径时两边要一起改。

### 口径

1. **一条分红方案 = 一个日历条目**，不按日期拆成多条 ——
   登记日和除权日差一个交易日，拆两条会让同一笔分红在日历里出现两遍。
   两个日期都写在事件的说明里。
2. **落点日期优先用除权除息日**，没有就退回股权登记日；
   两个都没有（只有报告期）**不进日历** —— 报告期不是「哪天除权」。
   实测当前清单里有 11 笔方案停在「董事会决议通过 / 预披露」，日期还没定，
   它们要等实施公告出来才进日历。
3. **已取消的方案不进日历**（进度含「取消 / 不分配 / 终止」）。
4. **UID 不含金额**：派息额在预案与实施公告之间会改（10 派 4.2 元 → 10 派 4.5 元）。
   金额进了 UID，日历 App 会当成两条事件 —— 用户的日历里会同时留着「预计」和「已实施」。
   金额写在说明里，同一个 UID 的内容变了，日历 App 会**就地更新**那一条。
5. **事件类型分开**：`分红` 与 `公告` 是两类，订阅方可以在日历 App 里按分类过滤。

### 产物是**幂等**的

产物里**不写「生成时间」**，`DTSTAMP` 也取自数据本身（公告日 / 方案公告日），
所以**数据没变 → 产物字节级不变 → 仓库不会产生无意义的提交**。
这跟中行净值那条流水线「没有新增数据就不产生文件」是同一个思路。

唯一随时间滑动的是 `分红` 事件的回看窗口（默认 180 天）：
只有当天正好有事件跨过这个边界，文件才会变一次。

### 产物

| 文件 | 内容 |
| --- | --- |
| `calendar/dividend-calendar.ics` | **日历订阅**（订阅这个） |
| `calendar/dividend-announcements.json` | 抓到的分红公告（结构化） |
| `calendar/dividend-announcements.csv` | 同上（表格，方便瞄一眼） |
| `calendar/dividend-plans.json` | 抓到的分红方案（登记日 / 除权日 / 派息） |

### 本地跑一次

需要 Node 18+（零第三方依赖，只用内建 `node:https` / `node:dns`）：

```bash
node scripts/fetch-dividend-calendar.mjs                    # 抓取并写产物
node scripts/fetch-dividend-calendar.mjs --dry-run          # 只抓不写，打印摘要
node scripts/fetch-dividend-calendar.mjs --selftest         # 自测（不联网）
node scripts/fetch-dividend-calendar.mjs --codes 600660,600036   # 只抓指定代码
node scripts/fetch-dividend-calendar.mjs --history-days 0        # 只留未来的分红事件
node scripts/fetch-dividend-calendar.mjs --plan-window-days 2000 # 把方案历史全写进仓库
```

| 参数 | 说明 |
| --- | --- |
| `--history-days N` | `分红` 事件的回看天数（默认 180；0 = 只留未来的） |
| `--announcement-days N` | `公告` 事件在日历里保留的天数（默认 60） |
| `--announcement-window-days N` | 抓公告的时间窗口（默认 400） |
| `--plan-window-days N` | 分红方案写进产物的窗口（默认 400；0 = 全量历史） |
| `--codes a,b` | 只抓指定代码 |
| `--as-of YYYY-MM-DD` | 指定「今天」（影响窗口判定；默认 = 北京时间今天） |
| `--dry-run` | 只抓不写 |
| `--selftest` | 自测（不联网） |

### 自测

日历订阅的错误**在抓取阶段看不出来**：一行超了 75 字节、UID 变了、转义顺序写反了 ——
数据照样抓到，但用户的日历 App 里会多出重复事件、或者干脆收不到。

所以脚本带一个 `--selftest`（不联网，只测纯函数），抓之前先跑：

- ICS 转义顺序（**先转义反斜杠**，再转义分号与逗号 —— 反过来会把新加的反斜杠再转义一次）
- 折行：每行 ≤ 75 **字节**、续行以空格开头、**不切坏 UTF-8**（一个汉字 3 字节）
- 落点日期的优先级、已取消的方案被排除
- UID 稳定性（**金额变了 UID 不变** → 日历就地更新，而不是多出一条）
- 方案 ↔ 公告的对应关系（优先实施公告，退到预案公告）
- 产物的结构（`BEGIN`/`END` 配对、每个事件有 UID/DTSTAMP/DTSTART/DTEND、无重复 UID）
- 两次生成字节一致（幂等）

## 限制

### 中行净值

- **补不了合并之前的历史** —— 中行页面上没有就永远没有。
- **被新披露覆盖的批次补不回来** —— 页面只留最新一条。
- **产品名偶有为空** —— 上游就是这样，脚本原样保留，不编造。
- **数据来自中行的展示口径**，与基金业协会的登记口径不一定一致；用于投资判断请以产品说明书和官方披露为准。

### 分红日历

- **只覆盖清单里那 50 只** —— 不在清单里的股票不进日历。
- **公告原文抓不到无限历史** —— 公告库一次只给最近的一批（脚本按 400 天窗口抓）。
- **方案还没定日期就不进日历** —— 停在「董事会决议通过 / 预披露」的方案要等实施公告出来。
- **公告与方案的对应靠日期** —— 对不上就在事件里标「未匹配到对应的分红公告原文」，不硬凑。
- **数据来自东方财富的整理口径**，与上市公司公告原文可能有个别出入；
  用于投资判断请以**公告原文**为准（事件里的链接就是原文）。

## 许可

中行净值数据来自中国银行公开披露页面；分红公告与分红方案来自东方财富公开接口，
并附有上市公司公告原文链接。本仓库只做数据留存与分析，不改变原值的含义。
